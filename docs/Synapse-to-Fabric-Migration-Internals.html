How each Synapse component is migrated to Microsoft Fabric

This document covers every component the accelerator moves. For each one it says what is read from Synapse, what the backend does with it, which Fabric API or SQL statement creates the result, what changes on the way, and what is left for a person. It was written from the accelerator's source code (src/discovery_agent/migration and api) as of 15 October 2026.

T-SQL  created by running SQL on the Warehouse REST  created as a Fabric item through the REST API Data  rows moved by a Fabric data pipeline Manual  left for a person, with the reason

End-to-end backend flow

The UI calls the local API (port 8001). The API runs every step below. Discovery only reads. The migration run is the only part that writes, and it writes only to Fabric.

Discover

Reads the Synapse workspace through the Artifacts API, the dedicated pool's catalog over ODBC, and optionally a Git repo. Everything is read-only, and catalog queries are SELECT-only by construction.

Plan

Puts objects in dependency-ordered waves, picks a strategy for each, runs preflight checks on every object's content, and scores readiness.

Configure

You switch stages on or off, choose options (collation, data mode, filters), and enter credentials. Credentials are kept in memory only.

Run

A background thread processes objects one at a time, in wave order and then kind order. Each object ends Completed, Skipped, Failed or Deferred.

Validate

Compares Synapse with Fabric object by object, including row counts. It can also check that items run in Fabric.

The three ways things move

Every component uses one of three mechanisms. This is the main distinction between scripts and actual data.

T-SQL on the Warehouse

Database objects are rebuilt as SQL statements and executed on the Warehouse SQL endpoint. Table structure is generated from catalog metadata. Views, procedures and functions use their own definition text after conversion rules have run.

Fabric item via REST

Workspace artifacts are converted from Synapse JSON to Fabric's definition format. The result is base64-encoded and posted to the Fabric REST API. Long-running creates are polled until they finish.

Fabric data pipeline

Table rows never pass through the accelerator. It generates a Fabric data pipeline whose Copy activity reads the Synapse pool and writes the Warehouse, then it runs the pipeline and compares row counts.

Tables (structure only)

T-SQL
Synapse
User tables (sys.tables, sys.columns, indexes)
Fabric
Empty Warehouse table
SQL
CREATE TABLE + ALTER TABLE … ADD CONSTRAINT
Stage
Warehouse & schema

A dedicated pool doesn't store CREATE TABLE text. The table is rebuilt from the column metadata discovery read from the catalog: name, type, length, precision, scale, nullability, identity and column order.

  1. The runner checks SELECT OBJECT_ID(?). If the table exists, it's left alone except that any missing dynamic data masks are added (see masks).
  2. It maps each column to a type the Warehouse supports (table below) and records a note for every change.
  3. It writes the column's dynamic data mask into the column definition (MASKED WITH (FUNCTION = '…')). The table therefore never exists unmasked, even while empty. If a mask uses a function Fabric doesn't have, the table is not created at all, so its rows can never be loaded unmasked.
  4. IDENTITY columns stay IDENTITY. Fabric supports IDENTITY only on bigint, with no seed or increment, so an int IDENTITY becomes bigint IDENTITY NOT NULL.
  5. It drops DISTRIBUTION, clustered columnstore, heap and partition settings, because the Warehouse manages storage itself. A note records the original distribution.
  6. It runs the CREATE TABLE. Then, for each primary key and unique constraint, it runs ALTER TABLE … ADD CONSTRAINT … NONCLUSTERED (…) NOT ENFORCED. Synapse already holds these as NOT ENFORCED. If Fabric refuses one, the table still counts as created and the refusal goes into the notes.
  7. The table is left empty. The Table data stage loads its rows.

Table data (the rows)

Data
Synapse
Rows of each migrated table
Fabric
Rows in the Warehouse table
Carried by
Generated Fabric data pipeline, one per wave
Stage
Table data (needs Warehouse)

The accelerator doesn't copy any data itself. It generates and runs a Fabric data pipeline, the bulk-copy tool built into Fabric. Each table in the plan gets its own “(data)” item in the run, so results are reported table by table. The first data item of a wave to start picks up every pending table in that wave and loads them together with one pipeline.

1 · Decide which tables need rows

  • External tables are skipped because they hold no rows in the pool and become shortcuts instead. Tables with no discovered columns, or more than 1,024 columns, fail.
  • The table must already exist in the Warehouse (Warehouse stage). If it doesn't, that item fails and tells you to run that stage first.
  • The runner counts the rows already in the Warehouse table. What happens next depends on the If a table already has rows option:
    • Skip it (default): a table with rows is left alone, so re-runs are safe.
    • Replace it: the pipeline runs TRUNCATE TABLE before copying.

2 · The connection to Synapse

The pipeline reads the pool through a Fabric SQL connection named synapse-{workspace}-{pool}. If a connection with that name exists, or any connection whose path contains the pool's server and database, it's reused. Otherwise one is created from the credentials you entered in the Table data stage. The options are a SQL login, a service principal, a Key Vault reference, or the workspace identity. Synapse never gives out its secrets, so without credentials these items are marked Deferred: needs the Synapse pool connection.

3 · The pipeline the accelerator generates

Name: load_{warehouse}_wave_{n}. The same wave always maps to the same pipeline, so it's reused on later runs. It is metadata-driven. A tables array parameter holds one entry per table, and each entry carries everything the copy needs:

{ "schema": "dbo", "table": "Trips",
  "query": "SELECT [TripId], [Pickup], [Geo].STAsBinary() AS [Geo], ... FROM [dbo].[Trips]",
  "preCopyScript": "TRUNCATE TABLE [dbo].[Trips]",   // only with "Replace it"
  "postCopyScript": "", "postCopyCleanup": "" }      // filled for IDENTITY tables

  • Source: SqlDWSource with the table's SELECT, through the Fabric connection, with a 2-hour query timeout. Columns a Copy activity can't carry are converted in the SELECT: geography/geometry → .STAsBinary(), xml → nvarchar(max).
  • Sink: DataWarehouseSink with allowCopyCommand: true. The Warehouse's COPY command loads the rows. Staging is switched on because COPY can't read a Synapse source directly, so the Copy activity stages the rows in the workspace first.
  • Types: the tabular translator converts every other type into the type the Warehouse column was created with.
  • Policy: 12-hour timeout per activity, 2 retries 60 seconds apart.

4 · Tables with an IDENTITY column

The original key values are kept. The table is loaded through a staging copy, which is the path Microsoft documents for Fabric Data Warehouse:

  1. A staging table with the same columns and masks but no IDENTITY is created in schema migration_load.
  2. The Copy activity writes the rows into the staging table unchanged.
  3. The “After copy” Script activity runs SET IDENTITY_INSERT … ON; INSERT INTO target (cols) SELECT cols FROM staging; SET IDENTITY_INSERT … OFF;
  4. A second script empties the staging table and runs DBCC CHECKIDENT('target', RESEED) so new rows continue after the loaded keys. It runs only if the move succeeded.

5 · Run, wait, verify

  1. What happens next depends on the What the stage does option. With Create only, the pipeline is created and the items say “Pipeline ready; run it in Fabric”. With Create and run (default), the runner starts it with POST …/items/{id}/jobs/instances?jobType=Pipeline and passes only this run's table list as the tables parameter.
  2. It polls the job every 20 seconds for up to 6 hours, and the item shows how many minutes it has been running.
  3. When the job completes, it runs SELECT COUNT_BIG(*) on both sides. Synapse is counted with the same filter that was used to load. Equal counts make the item Completed with “counts match”. Different counts make it Failed: Row counts do not match, showing both numbers.
  4. If the pipeline fails, each table gets Fabric's failure reason and a suggestion to retry with “Replace”.

Date filters and keeping tables in sync

Data

By default a whole table is copied. In Plan, you can give a table a filter instead:

Scope: which rows

A date column with a fixed from date (inclusive) and/or to date (exclusive). Dates are fixed when the plan is made, not relative to today, so every run copies and validates the same rows. The pipeline entry's query gets a WHERE clause.

Sync: keep loading new changes

A change column (such as modified_at) that moves when a row is added or changed, plus key columns. By default these are the table's own primary key or unique constraint. A synced table can't have an end date.

What happens for a synced table

  1. The runner reads the newest change value from Synapse. This is the watermark.
  2. It creates the control table migration_sync.sync_tables in the Warehouse if it's missing, plus a staging table for this table. It then registers one row: the table, its watermark, and the SQL each sync runs.
  3. The first load copies the rows in scope up to the watermark, through the normal wave pipeline.
  4. It creates one sync pipeline per Warehouse, sync_{warehouse}, with a daily 02:00 UTC schedule that is switched off. When you switch it on, each run works one table at a time:
    • Lookup: read the table list from the control table.
    • Lookup: the newest change in Synapse.
    • Copy: rows changed since the watermark go into the staging table. The window also re-reads the last hour or day, so rows committed late are caught.
    • Script: in one Warehouse transaction, replace rows that match on the key, insert the rest, and move the watermark forward.

A failed step leaves the watermark where it was, so the next run copies the same window again. Adding a table to sync only adds a row to the control table. The pipeline itself never changes.

Limits stated by the code: rows hard-deleted in Synapse leave nothing to copy, so they stay in the Warehouse. A soft delete that also moves the change column does carry over. Without key columns, a changed row can't be matched, so it arrives as an extra row. The runner refuses to load a synced table while the sync schedule is on, because the two would lose or duplicate rows.

Views, stored procedures and functions

T-SQL
Synapse
Definition text from sys.sql_modules
Fabric
Same object in the Warehouse
SQL
The converted CREATE … statement
Stage
Warehouse & schema

These are scripts, and they're migrated from their own text, which is the most faithful source available. The text goes through deterministic rewrite rules, and the result runs on the Warehouse.

  1. If the definition couldn't be read (encrypted, or VIEW DEFINITION not granted), the object fails with that reason.
  2. If the object already exists, it's skipped. With the update existing option it's rewritten as CREATE OR ALTER instead, which updates it in place and keeps the old version if Fabric rejects the new text.
  3. The T-SQL rules run (list below). They work on a masked copy of the text, so strings, quoted identifiers and comments are never changed by accident. Every removed statement is replaced by a /* removed for Fabric: … */ comment, so the change stays visible in Fabric.
  4. Direct storage paths are rewritten to OneLake if storage routing is set up (see routing).
  5. The statement runs on the Warehouse. If Fabric rejects it, the object fails with the server's own error message so you can fix it.

Rewrite rules

In Synapse codeWhat the rule does
WITH (DISTRIBUTION = …, CLUSTERED COLUMNSTORE INDEX, HEAP, PARTITION (…)) on CREATE TABLE / CTASRemoved. Fabric manages storage.
RENAME OBJECT a TO bRewritten as EXEC sp_rename N'a', N'b'
SET TRANSACTION ISOLATION LEVEL … (not SNAPSHOT)Removed. The Warehouse always uses snapshot isolation.
CREATE/ALTER/DROP WORKLOAD GROUP | CLASSIFIER, sp_addrolemember 'largerc', …Removed. Fabric has no workload management.
COPY INTO … CREDENTIAL = (IDENTITY = 'Managed Identity'), including inside dynamic SQL stringsCredential removed. COPY then reads storage as the Entra identity running it, which needs Storage Blob Data Reader.
SET IDENTITY_INSERT t ON|OFFKept. Removed only for tables that have no IDENTITY in the Warehouse.

Before the run, preflight flags whatever is left that a Warehouse is known to reject, so you see it as a plan risk instead of a mid-run failure: sys.pdw_* views, materialized views, SET ROWCOUNT, FOR XML, synonyms, PREDICT, CREATE USER and triggers.

Functions

Scalar functions and inline table-valued functions are created like views, before the views and procedures that call them. Multi-statement table-valued functions aren't supported by Fabric Warehouse, so they're deferred. You can bring one back by accepting an LLM-assisted rewrite as an inline function or a view (see LLM transforms), or by rewriting it by hand.

Roles, permissions and dynamic data masks

T-SQL
Synapse
Database principals, role members, permissions, masked columns
Fabric
Warehouse roles, members, GRANT/DENY, masks
SQL
CREATE ROLE, ALTER ROLE, GRANT, DENY
Stage
Roles & permissions (needs Warehouse)

Each role or user is one plan item. It's rebuilt from the catalog that discovery read. The run handles it after the objects it's granted on, in the same wave.

  1. Custom roles: CREATE ROLE, unless DATABASE_PRINCIPAL_ID says it already exists. Built-in roles such as db_datareader and public already exist, so only their members and permissions are applied.
  2. Members: ALTER ROLE [r] ADD MEMBER [m] for Entra users, Entra groups and nested roles. Built-in and resource-class members are skipped.
  3. Permissions: GRANT or DENY on the database, a schema (ON SCHEMA::), an object (ON OBJECT::) or individual columns, with WITH GRANT OPTION when it was set. Fabric creates an Entra user automatically on that user's first GRANT or DENY, so CREATE USER is never run.
  4. Every statement is attempted. If Fabric rejects some, the item fails and lists them, but the rest stay applied, and Retry re-applies everything safely.

Dynamic data masks

Masks travel with their tables rather than as a separate item. A new table gets MASKED WITH (FUNCTION = 'default()' | 'email()' | 'random(a,b)' | 'partial(…)') in its CREATE TABLE. An existing table gets ALTER TABLE … ALTER COLUMN … ADD MASKED for each mask it lacks. Adding a mask only hides data, so it never exposes anything.

Left for a person

  • SQL-authenticated users: Fabric has no SQL authentication. The item is deferred, and its reason contains the exact GRANT statements to run once you choose the Entra user or group that replaces it.
  • Resource-class roles (largerc, staticrc20 …) are dropped, because Fabric sizes queries itself.
  • CONNECT isn't carried, because workspace roles and item permissions decide who can connect in Fabric. Give these principals Read on the Warehouse in Fabric.

Notebooks

REST

Notebook resource (ipynb inside Synapse JSON)

API
POST /workspaces/{id}/notebooks (ipynb, base64)
Stage
Notebooks

Notebooks are code, so they're converted as a document and their cells keep their content. A few lines get mechanical rewrites.

  1. The notebook's language is mapped to Fabric's: PySpark → python, Spark → scala, SparkSQL → sql, SparkR → r. .NET (C#) notebooks can't be migrated and are deferred with “needs a rewrite”.
  2. It builds a plain ipynb document from the cells, keeping each cell's language override. Saved outputs are cleared.
  3. It drops Synapse-only settings and notes each one: the attached Spark pool (Fabric uses the workspace or Environment settings), session size settings, and the folder (the notebook goes to the workspace root).
  4. In Python cells it applies these rewrites:
    • mssparkutils.* → notebookutils.*. The from notebookutils import mssparkutils import is commented out because the module is built in.
    • The Synapse SQL connector com.microsoft.spark.sqlanalytics → Fabric's com.microsoft.spark.fabric.
    • spark.read.synapsesql("pool.schema.table") → reads "warehouse.schema.table" when the pool name differs from the Warehouse name.
  5. It doesn't rewrite the following. It flags them in the notes for review: TokenLibrary, synapsesql writes, linked-service credential calls, mssparkutils.env, and direct *.dfs.core.windows.net paths unless routing is on.
  6. It routes storage paths through OneLake shortcuts in every code cell when storage routing is set up.
  7. If a notebook with that name exists, it's skipped. With update existing, its definition is replaced through updateDefinition, which keeps its id so pipelines that call it still work.

Fabric pipelines use the same JSON family as Synapse, with three real differences the converter handles:

  • Datasets are inline. Fabric has no dataset item. Each Copy, Lookup, GetMetadata, Delete and Validation activity gets the dataset's settings embedded as datasetSettings, with @dataset().x parameters filled from what the activity passed. The connection is referenced by Fabric id. Dataset plan items complete as “Embedded in the pipelines that use it”.
  • Fabric items are referenced by id, so the notebooks, Spark jobs and child pipelines a pipeline calls must exist first.
  • The SQL pool is gone. Anything that read or wrote the migrated pool is pointed at the Warehouse.

  3. If anything it references is missing in Fabric (a connection, notebook or child pipeline), the pipeline fails and lists what to create first.
  4. If a pipeline with that name exists, it's skipped. With update existing, its definition is replaced in place, so callers and schedules keep pointing at it.

Storage path routing (applies across components)

REST

In Synapse, code reads abfss://container@account.dfs.core.windows.net/… as the workspace's managed identity. In Fabric it runs as the user. That often fails, for example when the storage account is in a different Entra tenant from Fabric. A Fabric connection with an account key or SAS still works across tenants, and a OneLake shortcut uses that connection.

If you map a storage account and container in Plan, the run:

  1. Creates one shortcut per container, named after the container, under Files in {warehouse}_lakehouse.
  2. Rewrites paths in notebooks, views, procedures, SQL scripts, pipeline SQL and Spark job files: 
    abfss://raw@acct.dfs.core.windows.net/x  →  abfss://<ws>@onelake.dfs.fabric.microsoft.com/<lh>/Files/raw/x
https://acct.dfs.core.windows.net/raw/x  →  https://onelake.dfs.fabric.microsoft.com/<ws>/<lh>/Files/raw/x
    Paths built from variables, such as f-strings or T-SQL string concatenation, are rewritten too when only one account is mapped.

LLM-assisted transforms (optional)

Some objects can't be converted by the rules, such as multi-statement functions, unusual T-SQL and notebooks with Synapse-only APIs. For these, you can ask for a draft from Claude through the local Claude Code CLI. No API key is used.

  1. On request, the object's source, the rule-based output and the project requirements (prompts/transform/project.md) are sent to the model. It runs with every tool switched off, in an empty folder, so it can only answer.
  2. The draft is checked and shown next to the source and the rule output. Nothing is deployed until a person accepts it, optionally after editing it.
  3. A run uses the accepted code instead of the rule-based conversion, but only while the source still matches what was accepted. T-SQL still goes through the rules afterwards to catch slips. The run log marks the object “LLM-assisted, reviewed”.

Setting MIGRATION_LLM=off turns generation off entirely.

Validation: how the result is checked

Validate reads both sides and writes nothing, unless you ask it to run items now. Each row is MATCH, REVIEW (an explained difference, or a check that couldn't run) or MISMATCH.

ComponentWhat is compared
Warehouse, schemasThat they exist and can be read.
TablesColumn names and types against the expected mapping; masks present. Converted types give REVIEW.
Table dataCOUNT_BIG(*) in Synapse and in Fabric, with the same filter. A synced table counts as in step anywhere between “up to the last watermark” and “everything now”.
Views, procedures, functionsDefinition text with whitespace and comments normalised. Differences give REVIEW (reformatted or converted).
Roles & permissionsThe role exists; members and every expected GRANT/DENY are present in sys.database_permissions.
NotebooksCell count.
PipelinesActivity count, including nested activities. Datasets: embedded in every pipeline that uses them.
Spark poolPool and Environment exist with the same node size and scale.
Connections, Spark jobs, SQL scripts, shortcutsThat they exist in Fabric.
SchedulesEach target pipeline has a schedule.

Runtime checks, which you choose to run, go further. Tables and views are queried with SELECT TOP (1). Procedures are compiled with sp_describe_first_result_set, and on request executed inside a transaction that's rolled back. Pipelines, notebooks and Spark jobs report their last Fabric run, or are run now on request; that is a real run. An object that matches but has never run in Fabric is REVIEW, because nothing proves it works yet.

Safety rules the run follows

  • Never overwrites. An object that exists in Fabric is skipped. The only exceptions are the explicit “update existing” option for notebooks, pipelines, Spark jobs, SQL scripts, views, procedures and functions, and masks being added to an existing table.
  • Re-runs are safe. Data loads skip tables that have rows unless you choose “Replace”. Shortcuts, connections, schedules and pipelines are reused by name.
  • Never runs anything early. Schedules and the sync schedule are created switched off.
  • Secrets aren't kept. Credentials live in memory for the run, go only into the Fabric create call, and are never logged or returned. Tokens stay inside the process.
  • Masked data is never exposed. A table whose mask can't be recreated isn't created, so its rows are never loaded.
  • Discovery is read-only. Catalog queries come from a fixed registry that's checked to be SELECT-only. The only writes go to the Fabric API and the Warehouse.
  • Every change is reported. Each converted type, removed clause, dropped setting and rewritten call appears as a note on the object and in the run log.
